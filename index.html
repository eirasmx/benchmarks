⚠ SYSTEM AUDIT — SPLASH NOT EXPLICITLY SHOWN
Confirmed in runtime.js · _boot(): _splashEl is extracted at step 4 but never explicitly forced to display:flex before await wasmInitPromise. The baseline CSS sets splash { display:flex } but if the browser hasn't painted before _injectBaselineCSS() runs, the splash may be invisible during WASM boot. Fix 6 adds if (_splashEl) _splashEl.style.display = "flex" immediately after step 4. Cost: 2 lines. Savings: perceived cold start collapses from ~148ms to ~10--20ms.

🔍 Fix 6 — Splash-first paint decoupled from boot
AUDIT FINDING perceived −80ms runtime.js easy · 2 lines
Confirmed in runtime.js · _boot(): _splashEl is extracted at step 4 but never explicitly forced visible before await wasmInitPromise. The baseline CSS sets splash { display:flex }, but no code path guarantees the splash is painted before WASM begins loading. Fix: after _splashEl = _appEl.querySelector(":scope > splash"), immediately force _splashEl.style.display = "flex". This costs ~0ms wall-clock and collapses perceived cold start from ~148ms to ~10--20ms (first HTML paint).
Current — runtime.js step 4
// 4. Extract splash (sync) _splashEl = _appEl .querySelector(":scope > splash") ?? null; // splash extracted but NOT forced // visible before WASM await // … DOM work … _runtime = await wasmInitPromise;
Fix — add step 4a
// 4. Extract splash (sync) _splashEl = _appEl .querySelector(”:scope > splash”) ?? null; // 4a. Force visible immediately if (_splashEl) { _splashEl.style.display = “flex”; } // … DOM work … _runtime = await wasmInitPromise;
🥇 Fix 3 — Parallelize ir.json with WASM compile
−12ms wasm-bridge.js easy
Confirmed in wasm-bridge.js · init(): _loadIR() is awaited sequentially after WASM instantiation. But ir.json is an independent network request — it needs no WASM APIs to start. Kick off the fetch(irUrl) immediately alongside the WASM glue import, then register bindings once both are ready via Promise.all. The ir.json payload (~8--25KB) often arrives before WASM compile finishes, making registration cost ~0 wall-time.
Before — serial
await wasmMod.default(...) // ir.json waits for compile await _loadIR(runtime, irUrl)
After — parallel
const irFetch = fetch(irUrl) await wasmMod.default(...) // irFetch already in flight await _loadIR(runtime, irFetch)
🥈 Fix 4 — <link rel="modulepreload"> via packager
−15--25ms clera_packager.py medium
Confirmed in clera_packager.py · _build_html(): no preload hints are injected for CRE assets. The browser doesn't know about cre.wasm, cre_runtime.js, or ir.json until clera.js is parsed and WASMBridge.init() runs — ~30--50ms of dead network time. The packager should inject three preload hints into <head> at build time so the browser pre-fetches in parallel with HTML parsing.
Packager injects into <head>
<link rel="preload" href="__cre__/wasm/cre.wasm" as="fetch" crossorigin> <link rel="modulepreload" href="__cre__/wasm/cre_runtime.js"> <link rel="preload" href="__cre__/wasm/ir.json" as="fetch" crossorigin>
Effect on boot timeline
HTML parse begins ↓ browser sees preloads ↓ all 3 fetches start JS evaluates (clera.js) ↓ WASMBridge.init() ↓ assets already cached
🥈 Fix 5 — Inline ir.json into HTML at build time
−12ms RTT clera_packager.py + wasm-bridge.js medium
ir.json is build-time static — it never changes at runtime. The packager can inline it directly into index.html as <script id="cre-ir" type="application/json">. _loadIR() checks for this element before fetching: if present, parse from DOM (sync, zero network). Eliminates the ir.json RTT entirely. Add a packager flag --inline-ir to opt in. If combined with Fix 3, Fix 3 becomes a no-op for the inline path.
packager: _build_html()
ir_json = json.dumps(ir) html = html.replace( '</body>', f'<script id="cre-ir" type="application/json"> {ir_json}</script>\n</body>' )
wasm-bridge.js: _loadIR()
const el = document.getElementById('cre-ir') if (el) { ir = JSON.parse(el.textContent) } else { const r = await fetch(irUrl) ir = await r.json() }
🥉 Fix 7 — Streaming WASM compilation
−10--20ms (first visit) wasm-bridge.js medium
WebAssembly.compileStreaming(fetch(url)) starts the compiler as bytes arrive over the network, rather than waiting for the full download. V8's Liftoff tier-1 compiler can typically keep up with a 4G stream, so by the time the last byte lands, compilation is already done. Only relevant for the first-visit slow path — IDB cache skips it on repeats. The produced WebAssembly.Module can be stored directly to IDB, replacing the current wasm-bindgen-driven compile. Requires Content-Type: application/wasm from the server — the packager dev server config should assert this.
⚙️ Fix 8 — cre_runtime.js script tag (eliminate dynamic import round-trip)
−5ms clera_packager.py + wasm-bridge.js low-risk
Confirmed in wasm-bridge.js · init(): cre_runtime.js is loaded via await import(glueUrl) where glueUrl is derived by string-replacing cre.wasm with cre_runtime.js in the absolute WASM URL. This dynamic import only fires after JS starts executing. The packager can inject a <script type="module" src="__cre__/wasm/cre_runtime.js"> tag directly into HTML (alongside the Fix 4 preloads), eliminating the dynamic import scheduling delay and the URL-string-replacement hack.
